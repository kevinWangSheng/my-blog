AGENTS.md 到底该写什么

给 coding agent 写开工边界,难点不在写得多,而在写出那些真正会改变它下一步动作的内容。

Shawn 2026-06-18 · 约 9 分钟 Workflow Agents

为什么 README 不够

我前面写 AGENTS.md 这篇时,犯了一个很典型的问题:我把结论讲出来了,但证据给得不够。读者如果还不知道 AGENTS.md 是什么,开头就太快;读者如果想判断这些公开项目到底怎么写,又会觉得太像二手总结。

一个 coding agent 进项目,第一件事是建立"我现在能改什么、不能动什么"的边界。README 面向人,讲的是项目是什么、怎么跑;AGENTS.md 面向 agent,讲的是它该怎么动手、哪里是雷区。两者目标不同,混在一起两边都讲不清。

AGENTS.md 的价值密度,取决于其中有多少句话能改变 agent 的下一步动作。纯背景介绍接近于零。

三类真正有用的内容

把多个公开仓库的 AGENTS.md 拆开看,真正反复起作用的只有三类。其余多是不会被 agent 用到的装饰性说明。

一、稳定的事实与边界

长期不变、且会约束动作的事实:技术栈、部署目标、哪些目录是废弃实现不要恢复。这类信息让 agent 不必每次重新推断,也避免它"帮你"恢复你早就删掉的旧链路。

  • 构建与验证命令(agent 自验证时要用)
  • 禁区:哪些文件/目录不要动,为什么
  • secrets 走环境变量,绝不写进仓库

二、决策与执行的分工

哪些选择必须人来拍(技术栈、内容源、发布),哪些 agent 可以自闭环。把这条写清楚,agent 才知道什么时候该停下来问、什么时候该自己往前走。

经验

把"human 只在决策和验收两处介入"写进去,比列十条 todo 更能让 agent 自己跑完一轮而不中途打断你。

三、可执行的开发流程

用一段最小的伪流程,告诉 agent 一个任务从研究到发布要经过哪些阶段、每阶段产出什么。下面是一个精简示例:

AGENTS.md复制
# 开发流程(每阶段都有明确产出)
研究   → research.md        # agent 调研
决策   → DECISIONS.md (+D-)  # human 拍板
规划   → plan.md
实现 ⇄ 自验证            # 内循环:失败就回退,不打补丁
验收   → human 看预览
发布   → 仅验收通过后上线

# 边界
禁止("未经请求就 push/deploy 生产")
禁止("恢复已废弃的同步链路")

写多少算合适

下面这张表是我现在用的取舍标准:每一类内容,问一句"它会不会改变 agent 的下一步动作",答案决定它放哪、写多细。

内容类型会改变动作?放哪
技术栈 / 部署目标会AGENTS.md(稳定事实)
禁区与废弃实现会(防误恢复)AGENTS.md(边界)
当前任务 todo会但易变tasks.md(执行层)
项目背景故事基本不会README(给人看)

一个反例

很多 AGENTS.md 花大段写"本项目的愿景与历史"。这类内容读着充实,但 agent 不会因为读了它而改变任何一步动作——它属于 README.md,不属于这里。能删的背景越多,真正起作用的边界越显眼。

所以这一版我换了写法:先讲背景,再看公开项目原文,把每一段"会改变 agent 行为"的内容单独摘出来对照。结论没变,但现在每条主张后面都跟着可被检验的依据1。

  1. 这里"可检验"指 agent 自己能从命令输出或文件状态里证明,而不是靠记忆断言。
